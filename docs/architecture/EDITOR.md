# Архитектура инструментов разработки

## Назначение и расположение

Редакторы юнитов, навыков, поля и HUD являются инструментами разработчика. Они находятся в `tools/`, запускаются отдельно и исключаются из игровой сборки. Пользовательские редакторы в готовой игре не входят в текущий контракт. Руководства собраны в [../tools/README.md](../tools/README.md). Старые корневые `unit_editor.tscn` и `battle_ui_editor.tscn` служат только совместимыми ссылками на сцены в `tools/`, не содержат реализации и исключены из экспорта.

Редакторы и игра используют одни определения, валидацию и боевые фабрики. Копии боевых правил в инструментах запрещены. Реализация Godot Editor plugin не требуется; будущий адаптер Inspector обязан использовать ту же модель документов.

## Общие документы и зависимости

`BattleDocument` (прежнее имя `EditorDocument`) и `BattleDocumentSerializer` находятся в `features/content/battles/`. Это общий формат авторского боя для инструментов и обычной игры, без зависимости от `tools/`, UI, `SceneTree` или runtime-состояния. JSON схемы 1 сохранён без миграции содержимого.

Документ объединяет `document_id`, версию схемы, `BattleMapDefinition`, `BattleDefinition`, версии зависимых пакетов и метаданные авторинга. Карта и расстановка изменяются совместно. `TileMapLayer`, маркеры, Inspector и UI-контролы только отображают документ.

`UnitLibrary` в `features/content/units/` читает и проверяет JSON-определения, преобразует их в `ContentPackage` с namespace `custom_units` и зависимостью `core`. Определения юнитов и presentation создаются раздельно. Общий `ContentLoader` проверяет их вместе с базовыми пакетами. Ошибка любого определения блокирует новый снимок целиком; существующий `ContentSnapshot` не меняется. Чтение библиотеки в игре не создаёт каталоги и не копирует изображения.

`UILayoutDocument`, `UILayoutStore` и `UILayoutPresenter` остаются в `features/battle/ui/`: это общий presentation-контракт, используемый игровым HUD. Инструменты UI не являются зависимостью игры.

## Структура хранения

| Данные | Путь |
| --- | --- |
| Определения авторских юнитов | `content/authored/units/*.json` |
| Изображения библиотеки | `content/authored/assets/units/` |
| Документы боёв | `content/authored/battles/*.json` |
| Общая высота сетки | `content/authored/battle_grid_layout.cfg` |
| Оформление HUD | `content/authored/ui/*.json` |
| Импортированные изображения HUD | `content/authored/ui/assets/` |
| Стартовый бой и UI | `content/game_content.tres` |
| Вспомогательный экспорт документа | `content/authored/exports/<ID>/` |

Это исходный контент проекта, переносимый вместе с Git-репозиторием. `user://` используется для локальных настроек окна, логов и будущих сохранений игрока. Игра не читает прежние библиотеки AppData. Назначение стартового документа и UI из инструментов допускает только пути внутри `content/` и сохраняет переносимый `res://` путь.

## Интерфейс инструментов

`tools/common/editor_ui.gd` (`EditorUi`) — общая тёмная тема и фабрики виджетов трёх редакторов: шапка, карточки, формы «подпись — поле», строка состояния, отметка несохранённого черновика, горячие клавиши кнопок, диалог потери правок. Модуль не содержит правил контента, файлового ввода-вывода и не попадает в игровую сборку. Редактор поля применяет тему только к своему UI: пробный `BattleScreen` и встроенные редакторы остаются со своим оформлением.

Все три окна устроены одинаково: шапка с действиями и состоянием черновика, библиотека слева, карточки формы, контекстная справка или предпросмотр справа, строка состояния снизу. Строка состояния отделяет сообщение о последнем действии (цвет по важности) от постоянного итога проверки черновика. `Ctrl+S`, `Ctrl+Z`, `Ctrl+Y`/`Ctrl+Shift+Z`, `Ctrl+N`, `Ctrl+R` закреплены за кнопками; скрытые кнопки (встроенный редактор, пробный бой) клавиши не перехватывают, текстовые поля получают ввод раньше сокращений.

## Редактор поля

Точка входа: `tools/battles/battle_editor.tscn`. `BattleEditorShell` координирует workflow, `EditorBattleView` отображает карту и маркеры, `EditorStatePalette` показывает состояния. `EditCommand` и `EditorCommandHistory` находятся только в инструментах.

Все изменения карты и расстановки выполняются через обратимые команды: добавить, переместить, обновить, дублировать и удалить расстановку; добавить, обновить, удалить гекс; сменить фон. История ограничена 100 командами с полными снимками документа; новая правка очищает redo. UI не вызывает `BattleEngine`.

История: подряд идущие переименования поля объединяются `EditCommand.absorb()` в один шаг, снимок первой команды восстанавливает имя до набора. Редакторы юнитов и навыков так же объединяют набор имени.

`placement_id` — стабильный ID авторской расстановки; при запуске он становится уникальным runtime `unit_id`. Два экземпляра одного определения имеют разные `placement_id`. Компьютерный противник — обычная расстановка на стороне с `control_source = AI`, общим либо переопределённым профилем ИИ.

Стартовый документ редактора берётся из `content/game_content.tres`. В верхней строке можно выбрать сохранённое поле из `content/authored/battles/` или создать новое. `BattleLibrary` читает список через общий сериализатор; структурно ошибочные файлы видны, но недоступны для выбора. Новое поле получает независимые document/battle/map ID, чистую сетку 18×12, стороны и цель базового боя, без расстановки. Название хранится в необязательном строковом `display_name` JSON схемы 1 и меняется через обратимую команду. Старые файлы без названия отображаются по имени файла. Первое обычное сохранение нового поля создаёт отдельный файл по стабильному ID; если файл с этим именем принадлежит другому документу, редактор открывает «Сохранить как…» и ничего не перезаписывает. Переименование не меняет ID и путь. Список обновляется после сохранения либо вручную. Создание и выбор поля защищены подтверждением потери несохранённых правок.

Диалоги save/load открываются в `content/authored/battles/`; текущий полный путь виден в панели. Черновик с игровыми ошибками можно сохранить, но назначение стартовым и пробный запуск блокируются валидацией. Структурные ошибки JSON не заменяют открытый документ. Сохранение использует временный файл и резервное переименование, возвращая ошибки IO.

Валидация проверяет ID расстановок, определения юнитов, стороны, профили ИИ, существование стартовых клеток, занятость, совместимость управления и обязательную цель. Общий валидатор документа сверяет версии пакетов и для пробного, и для обычного запуска. Ошибочные данные не исправляются молча.

### Окно и инструменты

Редактор поля: меню «Файл» с ускорителями, полоса инструментов над картой с клавишами `V U B E A D T C O` (`EditorToolBar`), правая панель `BattleEditorInspector` с вкладками «Инспектор» (только карточки активного инструмента и выделения), «Поле» (документ, фон, сетка, окно) и «Проверка» (диагностика, число ошибок в заголовке). Мышь карты приходит через `gui_input` рабочей области в `EditorBattleView.handle_input()`: всплывающие окна и наложенные кнопки не рисуют по полю. Инструмент выбора перетаскивает фигуру; отпускание порождает `placement_moved`, а shell выполняет обычный `EditCommand.move_placement` с теми же запретами, что у расстановки. `Delete`, `Ctrl+D`, `Esc` удаляют, дублируют выбранное и снимают выбор. Выделение, ставшее недействительным после undo/удаления, сбрасывается; щелчок по отсутствующему гексу снимает и выбор юнита. Вписывание карты не затирает сообщение статуса. Имена и портреты юнитов кешируются на один `ContentSnapshot`. `BattleEditorShell` связывает панели с документом и командами; построение правой панели и правила видимости её карточек находятся в `BattleEditorInspector`, который не знает о документе.

### Визуальный workflow

Поддержаны поле и маркеры, поиск и палитра юнитов, размещение и перенос, стороны и AI override, добавление/удаление клеток, undo/redo, JSON save/load/save-as, диагностика, пробный бой и назначение стартового боя игры.

Состояния наносятся и стираются кистью через общий `HexStateCatalog`. Форма ограничена максимальной рамкой 18×12; удаление занятого гекса требует убрать фигуру. Сетка и фигуры скрываются независимо. Сохраняются `hex_state_id`, `background_id` и `presentation_frame`; старые JSON схемы 1 получают совместимые значения по умолчанию.

Редактор карты продолжает сохранять готовые состояния: runtime-матрица и цепное распространение исполняются ядром при пробном/обычном запуске, а не изменяют авторский документ. Контракт — HEX_AND_UNIT_STATES.md.

Список фонов на вкладке «Поле» использует общий `BattleBackdrops`: три исходных мира и две инопланетные арены — открытая и с кристаллами по краям. Обе новые подложки — непрозрачные PNG 2560×1440, отображаемые в общей рамке 1920×1080. Выбор меняет только `background_id` через `EditCommand`, поддерживает undo/redo и сохраняется в JSON; пробный и обычный бой используют тот же каталог. Нарисованные кристаллы первого варианта не создают игровых препятствий.

`EditorGridLayoutControls` на вкладке «Поле» задаёт вертикальное смещение всей сетки: число в пикселях холста 1920×1080 и кнопки «Выше»/«Ниже» с шагом 10. Диапазон −540…540; отрицательное значение поднимает поле. Меняются клетки, фигуры, состояния, препятствия и hit testing, фон остаётся на месте. `EditCommand.set_grid_offset` обеспечивает undo/redo. Необязательный `map.grid_offset_y` JSON схемы 1 задаёт индивидуальную высоту; его отсутствие означает наследование общего значения, а явный 0 фиксирует исходную высоту. Экспортируемый `BattleMapDefinition.has_custom_grid_offset` сохраняет это различие при deep-copy/snapshot.

«Сделать высотой по умолчанию» атомарно сохраняет текущую высоту в проектный `content/authored/battle_grid_layout.cfg` (исходно 0). Новые и старые поля без индивидуальной высоты наследуют её при открытии, не получая несохранённых правок; свои значения других полей сохраняются. Это отдельная операция над общим контентом, вне истории документа. «Использовать высоту по умолчанию» обратимой командой удаляет индивидуальную настройку. `BattleGridLayoutSettings` разрешает высоту только в presentation; пробный и обычный бой используют тот же default. Ошибка записи показывается в статусе и не сообщает об успешном сохранении. CFG включён в игровую сборку.

Геометрия образца: холст 1920×1080, гекс 94×78, центры (137 + 94·(q + r/2), 197 + 58,5·r). Фиксированная рамка сохраняет положение остальных клеток при удалении крайних. Масштаб и панорама относятся к виду: «−»/«+»/«Вписать» над картой, средняя кнопка панорамирует, колесо поле не масштабирует. `EditorDisplaySettings` меняет окно/полный экран без изменения документа; встроенное окно Godot управляется хостом.

### Препятствия

Редактор размещает и обновляет целое препятствие через `EditCommand.put_obstacle`; удаление, undo/redo и копирование документа сохраняют целостность объекта. Направление задаёт одну из шести осей. Выбор любого гекса загружает общие свойства; изменение сохраняет начальный гекс. Размещение очищает состояния под препятствием с восстановлением через undo. ПКМ удаляет целый объект. Кисть состояния пропускает такие клетки. Удаление части карты под объектом запрещено. ID новых препятствий генерируются случайно и проверяются на уникальность в документе.

Модель препятствия и его правила в бою: [BATTLE_MAP.md](BATTLE_MAP.md) «Препятствия местности».

### Защита документа и восстановление

Редактор боя сравнивает сериализованный черновик с последней успешно открытой/сохранённой версией. Открытие заменяющего документа и закрытие приложения требуют подтверждения при отличиях; отмена выбора файла сохраняет черновик. Успешная запись обновляет сохранённую версию. Размещение на непроходимом гексе отклоняется валидатором; кисть препятствия и панель свойств не могут заблокировать занятую клетку.

После восстановления библиотеки при отсутствии документа редактор загружает бой из `GameContentSettings`, обновляет список сторон, AI и путь. При наличии документа обновление библиотеки сохраняет черновик и историю.

Встроенный редактор юнитов не обрабатывает закрытие окна сам: редактор боя сначала спрашивает его через `request_close()`, затем проверяет черновик боя. Пробный бой, остановленный ошибкой после старта, остаётся на экране с сообщением до возврата автора; ошибка запуска по-прежнему сразу возвращает в редактор с диагностикой.

### Пробный и обычный запуск

```text
BattleDocument.duplicate_document()
→ validate(ContentSnapshot)
→ snapshot.with_battle_document(...)
→ BattleStartRequest
→ обычный BattleScreen / SimulationRunner
```

Пробный бой включает несохранённые правки; возвращение не переносит runtime-состояние в авторский документ. После результата экран остаётся до возвращения; ошибка запуска показывается автору.

Обычный запуск использует `ProjectBattleLoader` и `GameContentSettings`: библиотека проекта плюс штатные пакеты → чтение JSON → версии зависимостей → валидация → тот же request. `GameLauncher` вызывает `BattleScreen.setup` до добавления сцены; ошибка обязательного контента показывается и блокирует бой.

«Сделать стартовым боем» сохраняет текущие правки, проверяет сохранённый документ через общий загрузчик и меняет `battle_document_path`. Ошибка сохранения или проверки не назначает документ.

### Экспорт документа

`EditorPackageExporter` сохраняет manifest и документ в отдельный подкаталог `content/authored/exports/`. Этот каталог не содержит всех зависимостей и не является устанавливаемым модом. Подключение стартового боя работает непосредственно с проектным JSON; внешний manifest/ZIP/PCK loader остаётся будущей задачей.

## Редактор юнитов

Точка входа: `tools/units/unit_editor.tscn`. Документ — отдельный JSON-словарь, не расстановка. Форма является проекцией; undo/redo ограничен 100 снимками. Новый ID генерируется один раз, переименование сохраняет ID, копирование создаёт другой. Несохранённые правки проверяются при смене документа и закрытии.

Файл называется по ID без namespace. Обязательны схема 1, стабильный ID, имя, изображение, ОЗ, урон, тип/дальность атаки, передвижение и списки активных/пассивных умений. Изображения принадлежат presentation и ограничены библиотекой assets. Сохранение атомарно через временный файл и резервное переименование.

Редактор поля открывает редактор юнитов дочерней сценой. На возврате библиотека перечитывается и обновляет палитру/маркеры без замены документа карты и истории. При изменении другим процессом служит кнопка обновления. Это узкий доверенный проектный формат, не общий внешний мод-loader.

Редактор юнитов задаёт начальную броню и назначает пять базовых активных умений создания гексов из пакета core. Необязательное поле JSON armor совместимо с прежней схемой 1.

`UnitLibrary.validate()` разделён на `validate_structure()` и `validate_references()`. `read_document()` возвращает структурно корректный документ вместе с ошибкой ссылок на навыки, чтобы редактор мог его открыть и исправить; `load_content()` по-прежнему отклоняет такой файл, частично созданный снимок невозможен. Сообщения о полях используют русские названия.

### Выбор умений

`UnitEditor` показывает два `MenuButton`: «Активные умения» и «Пассивные умения». Отмечаемые элементы поддерживают множественный выбор; меню остаётся открытым при отметке, кнопка показывает число выбранных, tooltip — названия. Выбор меняет массивы `abilities`/`passives` через существующую историю черновика, поддерживает undo/redo, загрузку и сохранение JSON схемы 1. Выбранные названия перечислены под кнопкой; ссылка на отсутствующий навык показана отдельным отмеченным пунктом, чтобы её можно было снять. Каталоги — UnitLibrary и PassiveAbilityCatalog; правила боя в редактор не перенесены.

### Погибшие варианты

Погибшие ассеты хранятся отдельно от живого списка: `content/authored/assets/corpses/<basename>.png`. `UnitLibrary` автоматически соединяет пару при построении presentation; существующие JSON и создание новых юнитов используют один контракт без новой зависимости игры на инструменты. Редактор показывает найденную пару. `tools/units/unit_death_preview.tscn` визуально проигрывает все20 смертей через общий игровой UnitActor/UnitDeathAnimator; это инструмент разработки. Правила генерации и обязательное предложение погибшего варианта после живого закреплены в `AGENTS.md` и [../tools/UNITS.md](../tools/UNITS.md).

## Редактор навыков

`tools/skills/skill_editor.tscn` — отдельная сцена F6 и встроенный инструмент кнопки «Навыки…» в редакторе поля. Редактор только правит существующие активные и пассивные умения: создать умение, эффект или шаблон в нём нельзя ([DECISIONS.md](../DECISIONS.md)). JSON-документ владеет данными, форма является проекцией. Отмена/повтор хранит до 100 снимков; набор названия и описания отменяется одним шагом. Смена умения, категории и закрытие защищают несохранённые правки.

Правится:

- название и описание с переменными `AbilityDescription`, меню «Вставить переменную» и предпросмотр «В игре» с примерными уроном и дальностью атаки юнита;
- у активного умения — дальность (кроме умений с дальностью атаки), радиус области, перезарядка и начальная перезарядка;
- у эффектов — урон цели и остальных, тип урона, урон атаки юнита вместо чисел, накладываемое состояние и уровни, состояние гекса;
- у пассивного — бонус и тип урона атаки, накладываемое состояние и уровни, невосприимчивость.

Цель, флаги, отображение, состав и тип эффектов, призываемый юнит и ответный удар пассива только показываются. Для встроенных умений то же проверяет `SkillLibrary.validate()`, поэтому ручная правка JSON ограничение не обходит.

Форма строится только при открытии умения, отмене и повторе. Отдельная правка обновляет строку проверки, предпросмотр и доступность полей. Список библиотеки фильтруется из кэша без чтения диска; «Обновить» вызывает `SkillLibrary.reload()` и перечитывает файлы. «Исходные значения» подставляют встроенный вариант одним шагом отмены, сохранение такого черновика удаляет переопределение.

`SkillLibrary` в `features/content/skills/` проверяет JSON схемы 1, атомарно сохраняет и адаптирует определения к общим `AbilityDefinition`/`AbilityEffectDefinition`. Встроенные документы и юниты для призыва читаются из пакетов один раз за процесс: `GameContentSettings.read()` перезагружает все пакеты (около 0,6 с), и вызывать его на каждое изменение нельзя. Авторские файлы лежат в `content/authored/skills/`. Изменения подключаются при загрузке библиотеки или нового боя; открытый бой сохраняет собственный снимок. `SkillLibrary.validate()` объясняет ограничения по-русски; правила ядра остаются последней проверкой.

## Редактор HUD

Точка входа: `tools/battle_ui/battle_ui_editor.tscn`, внутренний workbench сохраняет собственный UID. `UILayoutCanvas` показывает настоящий HUD в SubViewport; `UILayoutInspector` выдаёт правки; `UILayoutEditCommand` фиксирует одну обратимую операцию. Во время жеста изменяется preview-копия, отпускание фиксирует команду, Escape отменяет жест.

Поддержаны дерево блоков, перемещение/resize, геометрия, текст с `{value}`, шрифт, цвета/alpha, рамка, импорт изображений, видимость, reset, undo/redo, JSON save/load/save-as. Минимальные размеры зависят также от содержимого. Новые игровые команды и отдельные динамические карточки очереди инструмент не создаёт. Preview-масштаб, панорама и раскрытие служебных панелей не сохраняются в документе. Смена документа/закрытие защищает несохранённые правки.

Импортированные изображения копируются в `content/authored/ui/assets/` по SHA-256. JSON содержит ссылки `res://`; перенос проекта включает изображения. Сохранение атомарно; JSON ограничен известными свойствами, типами и размерами. Новые изображения доступны preview до завершения импорта Godot; сборка использует импортированные Texture2D.

«Использовать в боях» сохраняет документ и назначает `ui_profile_path` в `content/game_content.tres`. Возврат стандартного оформления очищает это поле. Пробный бой загружает текущий стартовый бой с `ui_document_override`, не сохраняет выбор или результат боя.

## Не реализовано

Полный UI целей, зон, триггеров и кампаний, глобальная карта и диалоги, внешний мод-loader, полноценный Godot Editor plugin, переход диагностики ко всем типам проблем, шаблоны карт и массовые операции остаются отдельными задачами.
