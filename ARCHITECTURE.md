# Архитектура A_star — краткая памятка

## Главная идея

Проект разделён на небольшие системы. Правила боя не знают о сценах и интерфейсе, а интерфейс только показывает уже рассчитанный результат.

Основной путь данных:

```text
content/ → ContentSnapshot → BattleStartRequest
→ BattleSession → BattleEngine → события боя
→ BattleController → View / HUD / UnitActor
```

## Какая папка за что отвечает

### Корень проекта

- `content/` — игровые данные в `.tres`: юниты, карты, способности, сценарии и пакеты контента.
- `features/` — код игровых систем.
- `addons/` — сторонние плагины Godot. Игровую логику сюда не класть.
- `debug_battle_launcher.tscn` — быстрый запуск тестового боя.

### `features/battle/`

- `engine/` — правила боя: можно ли выполнить действие и как изменится состояние. Здесь не должно быть UI, сцен и анимаций.
- `commands/` — команды игрока или ИИ: переместиться, атаковать, завершить ход.
- `definitions/` — входные описания боя: карта, расстановка, цель и снимок контента.
- `session/` — жизненный цикл одного боя; передаёт команды в движок и хранит результат.
- `controller/` — связывает сессию, ввод и отображение. Сам не решает, разрешена ли атака или движение.
- `view/` — показ поля, событий, подсветок и HUD. Не изменяет правила и авторитетное состояние боя.
- `units/` — всё, что относится к юнитам:
  - `UnitDefinition` — постоянные игровые параметры;
  - `UnitState`/`UnitSnapshot` — состояние конкретного юнита в текущем бою;
  - `UnitActor` и presentation-определения — внешний вид.
- `map/` — логическая гекс-сетка и преобразование определения карты в поле боя.
- `art/`, `ui/`, `tiles/` — изображения, UI-ресурсы и тайлы; правил боя здесь нет.
- `tests/` — существующие технические проверки боя.

### Остальные системы

- `features/abilities/` — применение эффектов способностей через правила боя.
- `features/content/` — загрузка, сортировка и проверка содержимого `content/`.
- `features/campaign/` — прогресс кампании и переходы между сценариями.
- `features/editor/` — редактор карты и расстановки, сохранение и undo/redo.
- `features/simulation/` — запуск боя без графики для автобоя и массовых прогонов.

## Куда класть новую функцию

| Что добавляется | Куда смотреть сначала |
| --- | --- |
| Новое правило боя | `features/battle/engine/` |
| Новая команда игрока или ИИ | `features/battle/commands/` |
| Новые данные карты, боя или расстановки | `features/battle/definitions/` |
| Подсветка, анимация, HUD или визуальный эффект | `features/battle/view/` или `features/battle/ui/` |
| Новый вид юнита | presentation-ресурс в `content/` или `units/definitions/` |
| Новые характеристики юнита | `UnitDefinition`; текущее здоровье и позиция — только runtime-состояние |
| Новая способность | `features/abilities/` и её данные в `content/` |
| Загрузка или проверка игровых данных | `features/content/` |
| Функция редактора | `features/editor/` |
| Правило кампании | `features/campaign/` |

## Пять правил, которые нельзя нарушать

1. UI и акторы не меняют здоровье, позицию или ход напрямую — они отправляют команду.
2. `BattleEngine` не зависит от `Node`, сцен, текстур, ввода и анимаций.
3. Логика решает, **что произошло**; `view/` решает, **как это показать**.
4. Ошибка обязательных данных останавливает запуск. Ошибка необязательного VFX или картинки использует fallback и не ломает бой.
5. Feature flag добавляется только после явного согласия владельца проекта. Если флаг не просили, сначала нужно обсудить его необходимость.

## Как понять, что файл пора разделить

Попробуй описать его одной фразой. Если получается «делает это **и ещё** вот это», внутри, вероятно, смешаны разные ответственности.

Хорошая граница позволяет заменить или удалить одну часть без переписывания правил соседних систем.
