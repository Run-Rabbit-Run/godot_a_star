# A_star: карта проекта и правила изменений

## Назначение

Этот репозиторий — Godot 4.7-проект A_star. Архитектура — модульный монолит с независимым ядром боя и адаптерами игры, редактора и симуляции. Каждая подсистема должна описываться одной фразой и меняться без чтения всего проекта.

## Точки входа

- `debug_battle_launcher.tscn` — графический запуск тестового боя.
- `features/battle/battle_screen.tscn` — адаптер одного графического боя.
- `features/editor/battle_editor.tscn` — пользовательский редактор карты и расстановки.
- `features/campaign/debug_campaign_simulation_launcher.tscn` — headless-прогон кампании.
- `project.godot` — настройки приложения; текущая main scene предназначена для отладки, а не для продуктового меню.

## Карта модулей

| Путь | Одна ответственность | Допустимые зависимости |
| --- | --- | --- |
| `features/battle/engine/` | Рассчитывает правила и изменяет авторитетное состояние боя | Команды, определения, способности и обычные типы Godot; без `Node`, сцен, UI и Tween |
| `features/battle/session/` | Координирует жизненный цикл боя и источники команд | `engine`, `commands`, `definitions`; без представления |
| `features/battle/commands/` | Описывает намерения участника боя | Только DTO и идентификаторы |
| `features/battle/definitions/` | Хранит проверяемые входные данные боя | Карта, юниты, способности и контент; без runtime-визуала |
| `features/battle/map/` | Преобразует определения карты в логическую сетку | `engine`; `BattleMapAssembler` — временный адаптер `TileMapLayer` |
| `features/battle/units/` | Разделяет логическое состояние юнита и графического актора | `UnitState*` не зависит от сцен; `UnitActor*` относится к представлению |
| `features/battle/view/` | Показывает события боя и принимает намерения пользователя | Снимки и события, но не прямое изменение `BattleState` |
| `features/battle/controller/` | Связывает сессию, ввод и представление графического боя | Не принимает решений о легальности команд |
| `features/abilities/` | Выполняет композицию зарегистрированных эффектов | `BattleState` через ограниченный контекст; без графики |
| `features/content/` | Загружает, упорядочивает и валидирует пакеты контента | Определения; без состояния боя и UI |
| `features/simulation/` | Запускает бой без графики с пределами и отменой | `BattleSession`; без сцен и анимационных ожиданий |
| `features/campaign/` | Ведёт переходы сценариев и прогресс кампании | Результаты боя и контент; без боевых акторов |
| `features/editor/` | Редактирует `EditorDocument`, поддерживает undo/redo, сохранение и пробный запуск | Общие валидаторы и фабрики; не копирует боевые правила |
| `content/` | Содержит базовые пакеты и определения | Не содержит runtime-состояние |

## Нельзя нарушать

- `BattleEngine`, `BattleState`, `BattleSession` и `SimulationRunner` не зависят от `SceneTree`, `Node`, `PackedScene`, `Texture2D`, ввода или анимации.
- `BattleScreen` получает `BattleStartRequest` и возвращает `BattleResult`; он не изменяет кампанию напрямую.
- `ContentSnapshot` — единый проверенный снимок контента для игры, редактора и симуляции.
- `UnitDefinition` хранит правила и `presentation_id`; сцены, текстуры, звук и визуальные параметры принадлежат отдельному presentation-определению.
- `BackgroundLayer` остаётся только визуальной подложкой. Существование клетки задаёт явный `BattleMapDefinition`; отсутствие клетки не равно заблокированной клетке.
- Скорость воспроизведения влияет только на представление и никогда не меняет результат боя.
- Редактор меняет документ через `EditCommand`; пробный бой не записывает runtime-состояние обратно в документ.
- Debug-launcher, smoke-проверки, редакторские инструменты и временные импортёры не становятся зависимостями игрового ядра.

## Feature flags

- Feature flag создаётся только после явного согласия пользователя.
- Если пользователь прямо попросил спрятать конкретную функцию за feature flag, это является согласием только для этой функции.
- Если пользователь не просил feature flag, но он кажется полезным, сначала сообщить: какую функцию предлагается переключать, зачем это нужно, какое значение будет по умолчанию и как будет удалён временный флаг. Затем дождаться согласия и только после него реализовывать флаг.
- Нельзя незаметно добавлять флаг «на всякий случай», подменять им полноценную валидацию или использовать его для сокрытия незавершённой обязательной логики.
- Одобренные флаги проверяются в точке композиции/запуска подсистемы, а не размазываются по правилам боя.

## Политика отказов

- Ошибка обязательных правил, определения, карты, расстановки или цели останавливает запуск до первого хода с явной диагностикой.
- Ошибка, после которой авторитетное состояние могло стать некорректным, завершает текущий бой; продолжать его в degraded mode нельзя.
- Необязательные presentation-подсистемы могут деградировать локально: отсутствующий VFX пропускается, отсутствующая картинка заменяется визуальным placeholder, необязательный звук отключается.
- Fallback не должен менять расчёт боя или молча заменять обязательный контент.
- Симуляторы и автоматические циклы обязаны иметь предел шагов, поддержку отмены и структурированный результат.

## Размер и декомпозиция

- Ограничение в 2 000 строк — аварийный потолок, а не целевой размер.
- Разделять файл раньше, если его описание требует «и ещё» или независимые части имеют разные причины изменения.
- Не создавать интерфейс или класс на каждый вызов. Новая граница нужна, когда часть можно проверить, заменить или удалить независимо.
- Координаторы могут знать несколько подсистем, но не должны содержать их правила, файловый ввод-вывод или конкретную отрисовку.

## Проверка изменений

По умолчанию сначала выполняются статические проверки из корня проекта:

```powershell
git status --short -- .
git diff --check -- .
git diff -- .
```

Не добавлять и не запускать автоматические тесты без отдельного разрешения пользователя. Статическая проверка не подтверждает интерактивный ввод, анимацию и визуальную читаемость; эти границы нужно указывать в отчёте.
